
# System Design Lab — API Testing

## 1. Purpose

Document API contracts, test scenarios, execution
commands, and results for the Order Management API.

Base URL: http://localhost:3000

Current implementation uses in-memory storage.
Test data resets when the server restarts.

## 2. Available Endpoints

| Method | Endpoint | Description | Success |
|--------|----------|-------------|---------|
| GET | /health | Health check | 200 |
| GET | /orders | List orders | 200 |
| GET | /orders/:id | Retrieve order | 200 |
| POST | /orders | Create order | 201 |

## 3. Test Execution

Start the application:

```bash
npm run dev
```

In another terminal, execute the curl commands below.

The `-i` flag displays response headers and status codes.

## 4. GET API Tests

### TC-001: Health Check

```bash
curl -i http://localhost:3000/health
```

Expected: HTTP 200 with status "ok".

### TC-002: Retrieve All Orders

```bash
curl -i http://localhost:3000/orders
```

Expected: HTTP 200 with an array of orders.

### TC-003: Retrieve Existing Order

```bash
curl -i http://localhost:3000/orders/1
```

Expected: HTTP 200 with order ID 1.

### TC-004: Retrieve Nonexistent Order

```bash
curl -i http://localhost:3000/orders/999
```

Expected: HTTP 404.

Response:

```json
{
  "error": "Order not found"
}
```

### TC-005: Invalid Order ID

```bash
curl -i http://localhost:3000/orders/abc
```

Expected: HTTP 400.

Response:

```json
{
  "error": "Invalid order ID. Must be a positive integer."
}
```

## 5. POST API Tests

### TC-006: Create Valid Order

```bash
curl -i -X POST http://localhost:3000/orders \
  -H "Content-Type: application/json" \
  -d '{"item":"Monitor","quantity":2}'
```

Expected:
- HTTP 201 Created
- Location header identifies the new resource
- Response contains generated ID
- Status is "created"

Observed: PASS — November 1, 2026.

### TC-007: Retrieve Newly Created Order

Run immediately after TC-006, using the ID returned
in the creation response.

Example:

```bash
curl -i http://localhost:3000/orders/3
```

Expected:
- HTTP 200
- Item is "Monitor"
- Quantity is 2
- Status is "created"

Observed: PASS — November 1, 2026.

### TC-008: Reject Negative Quantity

```bash
curl -i -X POST http://localhost:3000/orders \
  -H "Content-Type: application/json" \
  -d '{"item":"Monitor","quantity":-5}'
```

Expected: HTTP 400.

Response:

```json
{
  "error": "Valid item and positive integer quantity are required"
}
```

Observed: PASS — November 1, 2026.

### TC-009: Reject Missing Item

```bash
curl -i -X POST http://localhost:3000/orders \
  -H "Content-Type: application/json" \
  -d '{"quantity":2}'
```

Expected: HTTP 400.

Observed: PASS — November 1, 2026.

## 9. Engineering Considerations

### Test Isolation

Tests should not depend on execution order or
hardcoded IDs generated by previous tests.

### Contract Validation

Tests should validate response structure, types,
required fields, and relevant headers.

### Idempotency

Repeated POST requests may create duplicate orders.

Future experiments will explore idempotency keys
and retry-safe API design.

### Persistence

The current API stores data in memory. A successful
GET after POST confirms that the order exists in
the running process, not that it survives a restart.
